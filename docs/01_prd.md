## 1. Executive Summary & Quantified Success Metrics

### 1.1 Executive Summary
ProNet is a local-first, multi-user professional network application designed to replicate core LinkedIn platform workflows: rich professional identity management, bi-directional professional connection graphs with 1st- and 2nd-degree designations, activity feeds with algorithmic and chronological views, a job marketplace with a structured applicant pipeline, and direct messaging over persistent connections.

The system operates entirely on local infrastructure with zero third-party cloud dependencies, running against an optimized SQLite database in Write-Ahead Logging (WAL) mode. For rapid evaluation and development, the platform provides an instantaneous persona switching mechanism alongside pre-seeded professional profiles.

### 1.2 Quantified Success Metrics
All performance and operational criteria must satisfy the following deterministic numerical targets:

| Metric ID | Description | Target Value | Measurement Protocol |
|---|---|---|---|
| **KPI-001** | Feed Endpoint Latency (p95) | ≤ 150 ms | 20 posts per page with author summary, aggregated reaction counts, viewer reaction status, and preview comments under 20 concurrent simulated clients. |
| **KPI-002** | Profile & Degree Evaluation Latency (p95) | ≤ 80 ms | Profile fetch endpoint including 1st-degree connection count and mutual connection computation for 2nd-degree badge calculation. |
| **KPI-003** | Real-Time Direct Message Latency (p95) | ≤ 50 ms | Elapsed time from message transmission over WebSocket by Sender to receipt confirmation by Recipient client. |
| **KPI-004** | Initial Boot Seeding Duration | ≤ 3.0 s | Complete execution time for schema migration and deterministic population of 10 user personas, 15 connections, 12 feed posts, and 8 job listings. |
| **KPI-005** | Backend Process Memory Footprint | ≤ 250 MB RSS | Resident set size of the FastAPI application process after running continuous feed queries and 10 concurrent WebSocket connections. |
| **KPI-006** | Frontend Client Bundle Size | ≤ 1.2 MB | Total uncompressed JavaScript and CSS production distribution bundle generated by Vite. |
| **KPI-007** | Query Count Per Feed Page | Exact: 2 queries | One query for paginated post IDs/records, one batch query for related entities (`selectinload`/joined aggregate). Zero N+1 query patterns permitted. |

## 2. Scope Matrix

### 2.1 In-Scope (v1 Release)
1. **Persona Authentication & Quick Switcher:**
   - JSON Web Token (JWT) Bearer authentication (HS256).
   - Password hashing utilizing bcrypt with work factor 12.
   - Development-mode Quick Persona Switcher in the top navigation bar enabling 1-click account switching across the 10 seeded personas without re-authenticating.
2. **Professional Profile Management:**
   - Customizable profile attributes: Full Name, Professional Headline, Location, About/Bio summary, Avatar image URL.
   - Structured Work Experience timeline: Company, Role Title, Start Date, End Date (or "Present"), Location, Summary.
   - Education history: Institution, Degree, Field of Study, Start Year, End Year.
   - Skills inventory: Tag-based skills with add/remove capabilities.
   - Dynamic Degree Badges: "1st" degree for direct connections, "2nd" degree for non-connected users sharing at least one mutual 1st-degree connection.
3. **Bi-Directional Connection Graph:**
   - Connection lifecycle states: `PENDING`, `ACCEPTED`, `IGNORED`.
   - Actions: Send Connection Request (with optional text note up to 300 characters), Accept Request, Ignore Request, Cancel Outgoing Request, and Disconnect (remove existing connection).
   - State-machine collision guards preventing duplicate or reciprocal pending requests.
4. **Social Activity Feed:**
   - Post types: Plain text, code snippets (with syntax language label), and single image uploads (≤ 5 MB).
   - Dual-mode feed sorting: "Recent" (strict reverse-chronological by creation timestamp) and "Top" (engagement score calculated via: `(reactions * 2) + (comments * 3) + (is_connection * 5)` divided by post age in hours).
   - Global post visibility across all registered users, with connection posts weighted higher in the "Top" feed view.
   - Reactions: Three explicit types (`LIKE`, `CELEBRATE`, `INSIGHTFUL`) with toggle and switch capabilities.
   - Two-Level Threaded Comments: Root comments on posts (Level 1) and direct replies to comments (Level 2). Arbitrary deeper nesting is blocked.
   - Content Moderation: Users may edit or delete their own posts and comments; post authors have administrative permission to delete any comment placed on their post.
5. **Job Board & Mini-ATS:**
   - Job creation: Title, Company Name, Workplace Type (`REMOTE`, `HYBRID`, `ON_SITE`), Location, Salary Range (Min/Max), Description, and Required Skills tags.
   - Candidate discovery: Multi-facet filtering by keyword, location, workplace type, and skill tags.
   - "Easy Apply" submission: Automated snapshot pre-fill from applicant profile, optional text note to recruiter (≤ 500 characters), and optional PDF/DOCX resume file upload (≤ 5 MB).
   - Applicant tracking pipeline: Job author dashboard with candidate status progression (`APPLIED`, `REVIEWING`, `SHORTLISTED`, `REJECTED`).
6. **Real-Time Direct Messaging & Notifications:**
   - 1-on-1 private messaging restricted strictly to confirmed 1st-degree connections.
   - Full duplex WebSocket channel for live message transport and presence updates.
   - Top navigation notification badges with live counts for unread messages, pending connection requests, post reactions, and job application updates.
7. **Database Seeding:**
   - Deterministic seed script populating 10 complete professional profiles, 15 connection links, 12 rich posts with reactions and comments, and 8 job listings on initial clean run.

### 2.2 Out-of-Scope (Strictly Excluded)
1. Video and audio streaming, voice calls, screen sharing, or WebRTC media connections.
2. Paid subscription tiers, recurring billing, Stripe/payment gateway integrations.
3. Third-party OAuth authentication providers (Google, GitHub, Apple).
4. External transactional email or SMS delivery services (SMTP, SendGrid, Twilio).
5. Cloud object storage providers (AWS S3, Google Cloud Storage); all file uploads are persisted locally in `/uploads`.
6. Machine learning model training, embedding generation, or external vector database indexing.
7. Enterprise organization hierarchy, company page administration, or multi-seat team accounts.
8. Recursive comment nesting beyond Level 2 (Post → Comment → Reply).

## 3. Traceable Functional Requirements

### 3.1 Authentication & Persona Switching

#### REQ-001: Local Persona Quick-Switching
- **Priority:** P0
- **Persona:** Developer / QA Tester / Demo Evaluator
- **Description:** The system must provide a persistent dropdown in the navigation header displaying all 10 pre-seeded personas. Selecting a persona switches the active session immediately to that user without credential prompts.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` an authenticated or unauthenticated client viewing the application,
    - `When` the user selects "Elena Rostova (Staff AI Engineer)" from the Quick Switcher dropdown,
    - `Then` the system stores Elena's JWT in browser session storage, updates application state, and redirects the view to the feed reflecting Elena's identity and connection graph.
  - **Negative Path:**
    - `Given` a request payload targeting an invalid persona identifier `user_999`,
    - `When` the persona switch endpoint is called,
    - `Then` the system rejects the request with HTTP 404 Not Found and retains the prior active user session.

#### REQ-002: Standard Credential Authentication & Token Validation
- **Priority:** P0
- **Persona:** Professional User
- **Description:** Users can register with an email and password or log in to obtain an access token. All protected endpoints must validate the Bearer token.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` valid registration credentials (unique email, password length ≥ 8 characters),
    - `When` the user submits the registration form,
    - `Then` the system stores the password hashed via bcrypt (cost factor 12) and returns a signed JWT containing user ID and expiration timestamp (24 hours).
  - **Negative Path:**
    - `Given` an expired or tampered JWT in the `Authorization: Bearer <token>` header,
    - `When` the client makes a request to any protected endpoint,
    - `Then` the system returns HTTP 401 Unauthorized with error code `TOKEN_EXPIRED` or `INVALID_TOKEN`.

### 3.2 Profile & Social Graph

#### REQ-003: Professional Profile Editing
- **Priority:** P0
- **Persona:** Professional User
- **Description:** Users can view and update their profile information, including headline, summary, experience timeline items, education items, and skill tags.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` an authenticated user on their own profile page,
    - `When` the user adds a new experience entry with Title "Senior Systems Architect", Company "Acme Corp", Start Date "2022-01-01", and End Date null (Current),
    - `Then` the system persists the record and displays the entry sorted chronologically at the top of the experience section.
  - **Negative Path:**
    - `Given` an experience entry with Start Date "2024-01-01" and End Date "2022-01-01",
    - `When` the user submits the profile update,
    - `Then` the system rejects the request with HTTP 422 Unprocessable Entity specifying `END_DATE_BEFORE_START_DATE`.

#### REQ-004: Degree Calculation and Badge Display
- **Priority:** P0
- **Persona:** Professional User
- **Description:** When viewing another user's profile, the system must compute and display their relational degree badge relative to the authenticated viewer.
- **Acceptance Criteria:**
  - **Happy Path (1st Degree):**
    - `Given` User A and User B have an active connection with status `ACCEPTED`,
    - `When` User A views User B's profile,
    - `Then` the profile header displays a "1st" badge and enables the "Message" button.
  - **Happy Path (2nd Degree):**
    - `Given` User A is not directly connected to User C, but User A is connected to User B, and User B is connected to User C,
    - `When` User A views User C's profile,
    - `Then` the profile header displays a "2nd" badge and displays the count and avatars of mutual connections.
  - **Happy Path (3rd+ / Out of Network):**
    - `Given` User A and User D share zero mutual connections and have no direct connection,
    - `When` User A views User D's profile,
    - `Then` the profile header displays a "3rd+" badge and hides mutual connection summaries.

#### REQ-005: Outgoing Connection Request Submission
- **Priority:** P0
- **Persona:** Professional User
- **Description:** A user can send a connection request to any out-of-network professional with an optional message note up to 300 characters.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` User A and User B have no existing connection record,
    - `When` User A submits a connection request to User B with note "Excited to connect!",
    - `Then` the system creates a connection record with status `PENDING`, sets `initiator_id = User A`, and pushes a notification to User B.
  - **Negative Path (Duplicate Collision):**
    - `Given` User A has already sent a pending request to User B,
    - `When` User A attempts to submit a second request to User B,
    - `Then` the system rejects the action with HTTP 409 Conflict with code `CONNECTION_ALREADY_REQUESTED`.
  - **Negative Path (Reciprocal Collision):**
    - `Given` User B has already sent a pending request to User A,
    - `When` User A attempts to submit a connection request to User B,
    - `Then` the system intercepts the collision, transitions the existing record to `ACCEPTED`, and returns HTTP 200 with code `CONNECTION_AUTO_RESOLVED`.

#### REQ-006: Connection Request Acceptance and Ignorance
- **Priority:** P0
- **Persona:** Recipient User
- **Description:** A recipient of a pending connection request can accept or ignore the request.
- **Acceptance Criteria:**
  - **Happy Path (Accept):**
    - `Given` User B has a pending request from User A,
    - `When` User B clicks "Accept",
    - `Then` the connection status transitions to `ACCEPTED`, both users' connection counts increment by 1, and direct messaging between them unlocks.
  - **Happy Path (Ignore):**
    - `Given` User B has a pending request from User A,
    - `When` User B clicks "Ignore",
    - `Then` the connection status transitions to `IGNORED`, the request is removed from User B's pending list, and User A receives no negative notification.

#### REQ-007: Outgoing Connection Request Cancellation
- **Priority:** P1
- **Persona:** Sender User
- **Description:** A user can withdraw any pending connection request they previously initiated.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` User A has sent a pending connection request to User B,
    - `When` User A clicks "Withdraw Request",
    - `Then` the record is deleted from the database, and the target profile button resets to "Connect".
  - **Negative Path:**
    - `Given` User B has already accepted the request before User A attempts withdrawal,
    - `When` User A sends a withdrawal request,
    - `Then` the system returns HTTP 400 Bad Request with code `CANNOT_WITHDRAW_ACCEPTED_CONNECTION`.

#### REQ-008: Connection Removal (Disconnect)
- **Priority:** P1
- **Persona:** Professional User
- **Description:** Either party in an accepted 1st-degree connection can terminate the connection.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` User A and User B are 1st-degree connections,
    - `When` User A selects "Remove Connection" on User B's profile,
    - `Then` the connection record is deleted, direct messaging between them is locked, and feed prioritization between their posts is recalculated.

### 3.3 Activity Feed & Engagement

#### REQ-009: Rich Post Creation
- **Priority:** P0
- **Persona:** Content Creator
- **Description:** Users can publish posts containing text (up to 3,000 characters), an optional code block with designated programming language, or an optional attached image.
- **Acceptance Criteria:**
  - **Happy Path:**
    - `Given` an authenticated user on the feed page,
    - `When` the user enters text, attaches an image file of size 2.1 MB (`image/png`), and clicks "Post",
    - `Then` the system saves the image to `/uploads/posts/`, creates the post record, and displays it at the top of the feed within 200 ms.
  - **Negative Path (Oversized File):**
    - `Given` an attached image of size 6.5 MB,
    - `When` the user attempts to submit the post,
    - `Then` the client blocks upload and the backend returns HTTP 413 Payload Too Large with message `FILE_SIZE_EXCEEDS_5MB`.
  - **Negative Path (Disallowed Mime Type):**
    - `Given` an attached executable file `script.exe` renamed to `image.png`,
    - `When` the user submits the post,
    - `Then` the backend inspection of file magic bytes rejects the upload with HTTP 415 Unsupported Media Type.

#### REQ-010: Feed Consumption and Dual-Mode Sorting
- **Priority:** P0
- **Persona:** Professional User
- **Description:** Users can toggle between "Recent" (pure chronological order) and "Top" (engagement and network affinity weighted order) feeds with cursor-based pagination (20 items per page).
- **Acceptance Criteria:**
  - **Happy Path (Recent Mode):**
    - `Given` the user selects the "Recent" feed tab,
    - `When` the feed request is executed,
    - `Then` posts are returned strictly ordered by `created_at DESC`.
  - **Happy Path (Top Mode):**
    - `Given` the user selects the "Top" feed tab,
    - `When` the feed request is executed,
    - `Then` posts are sorted by the ranking formula: `((like_count + celebrate_count + insightful_count) * 2 + comment_count * 3 + (is_connection ? 5 : 0)) / ((hours_since_creation + 2) ^ 1.5) DESC`.
  - **Happy Path (Pagination):**
    - `Given` the user has scrolled to the 20th post,
    - `When` the bottom intersection trigger fires,
    - `Then` the next 20 posts are retrieved using the `cursor` timestamp parameter without duplicate items.

#### REQ-011: Multi-Type Post Reactions
- **Priority:** P0
- **Persona:** Professional User
- **Description:** Users can react to any post with one of three reaction types: `LIKE`, `CELEBRATE`, or `INSIGHTFUL`. A user may have only one active reaction per post at any time.
- **Acceptance Criteria:**
  - **Happy Path (Add Reaction):**
    - `Given` a user has not reacted to Post #42,
    - `When` the user clicks `CELEBRATE`,
    - `Then` the system increments the celebrate count by 1 and updates the user's active reaction state to `CELEBRATE`.
  - **Happy Path (Toggle Off Reaction):**
    - `Given` a user currently has an active `LIKE` on Post #42,
    - `When` the user clicks `LIKE` again,
    - `Then` the reaction is removed and the total like count decrements by 1.
  - **Happy Path (Switch Reaction):**
    - `Given` a user currently has an active `LIKE` on Post #42,
    - `When` the user clicks `INSIGHTFUL`,
    - `Then` the like count decrements by 1, the insightful count increments by 1, and the active state switches to `INSIGHTFUL`.

#### REQ-012: Two-Level Comment Threading & Moderation
- **Priority:** P0
- **Persona:** Professional User / Post Author
- **Description:** Users can add root comments to posts and single-level replies to comments. Post authors have moderation rights over all comments on their post.
- **Acceptance Criteria:**
  - **Happy Path (Root Comment):**
    - `Given` a post with ID 10,
    - `When` User B writes a comment with text "Great perspective!",
    - `Then` a Level 1 comment is created with `parent_id = null`.
  - **Happy Path (Reply):**
    - `Given` Level 1 comment with ID 100,
    - `When` User C submits a reply with `parent_id = 100`,
    - `Then` a Level 2 comment is created linked to comment 100.
  - **Negative Path (Sub-Reply Depth Restriction):**
    - `Given` Level 2 reply with ID 200,
    - `When` User D attempts to submit a reply with `parent_id = 200`,
    - `Then` the backend rejects the request with HTTP 400 Bad Request and error code `MAX_COMMENT_DEPTH_EXCEEDED`.
  - **Happy Path (Author Moderation):**
    - `Given` User A is the author of Post 10, and User B wrote comment 100 on it,
    - `When` User A clicks "Delete Comment" on comment 100,
    - `Then` comment 100 and all its child replies are deleted from the database.

#### REQ-015: "Easy Apply" Application Submission

#### REQ-016: Recruiter Pipeline Candidate Status Management

## 5. Edge-Case & Failure Mode Matrix

| ID | Failure / Edge Scenario | Trigger Condition | System Behavior & Mitigation Protocol | User-Visible Result |
|---|---|---|---|---|
| **EDG-001** | Simultaneous Connection Collision | User A sends request to User B at the exact time User B sends request to User A. | Database unique composite index on ordered pair `(min(user_a, user_b), max(user_a, user_b))` traps race condition. The second transaction detects pending incoming request and auto-transitions the record to `ACCEPTED`. | Both users immediately see each other as confirmed 1st-degree connections without error. |
| **EDG-002** | Unauthorized Messaging Attempt | User attempts to post message to a recipient who is not a 1st-degree connection. | Backend checks connection table for `status = 'ACCEPTED'`. Rejects request before creating message record or dispatching WebSocket packet. | Error notification: "You can only message confirmed 1st-degree connections." |
| **EDG-003** | Rapid Duplicate "Easy Apply" | Candidate double-clicks or submits concurrent requests for the same job listing. | Unique constraint on `(job_id, applicant_id)`. The second insert raises integrity error, rolling back transaction. | Primary submission succeeds; second submission displays "Application already submitted for this role." |
| **EDG-004** | File Extension / MIME Spoofing | User uploads an `.exe` file renamed to `resume.pdf` or `photo.jpg`. | Backend inspects initial file header magic bytes (e.g., `%PDF`, `\xFF\xD8\xFF`). If magic bytes do not match declared MIME type, upload is rejected and file is discarded. | HTTP 415 error banner: "File format is invalid or corrupted. Only genuine PDF, DOCX, PNG, and JPEG files are accepted." |
| **EDG-005** | Offline WebSocket Message Delivery | Sender posts a direct message while the recipient's WebSocket connection is disconnected. | Message record is persisted in SQLite with `read_at = NULL`. Notification record is inserted with `status = UNREAD`. When recipient establishes WebSocket, pending messages and unread counts are delivered on handshake. | Sender sees checkmark indicating message sent. Recipient sees unread badge count immediately upon logging in or reconnecting. |
| **EDG-006** | Orphaned Reply on Deleted Post | User submits a comment reply while the root post or parent comment is concurrently deleted by its author. | Foreign key constraint with `ON DELETE CASCADE` removes child entities. Comment submission query validates active existence of `post_id` and `parent_id`. | HTTP 404 error toast: "The post or comment you are replying to has been removed." |
| **EDG-007** | Self-Connection / Self-Reaction | User attempts to send connection request to self or react to their own post. | Backend validation asserts `sender_id != recipient_id`. Self-connections are blocked; self-reactions are permitted on social feed posts. | Attempting to connect to self produces HTTP 422: "You cannot establish a connection with yourself." |
| **EDG-008** | Token Expiration During Form Editing | JWT expires while user is drafting a long post or job description. | Frontend API client intercepts HTTP 401 response. Saves draft content in browser local storage, prompts user to re-authenticate or quick-switch, and restores draft upon re-login. | Modal prompt: "Your session has expired. Re-authenticate to save your draft." No data loss. |
